# Virtual Population Lab

A framework for generating and comparing synthetic populations from real tabular datasets using three interchangeable modeling engines: physics-informed Monte Carlo, traditional ML regression, and a generative VAE.

## Overview

Given a real dataset, this project generates several synthetic populations — one per engine — and evaluates which one best preserves the real population's feature distributions, correlations, and uncertainty. It's dataset-agnostic: everything specific to a dataset (which columns are features, what causal relationships to assume, whether the data is already scaled) lives in one config module, so pointing the pipeline at a new dataset means writing a new config, not touching the modeling code.


## The three engines

1. **Physics-informed Monte Carlo** (`src/generators/physics_mc_generator.py`)
   Samples from an assumed causal chain between features (e.g. size drives weight, ripeness drives sweetness) — each relationship is fit as a linear regression on the real data, so slopes/intercepts/noise are calibrated, not guessed. Every conditional is a Gaussian we can sample directly, so plain forward (ancestral) Monte Carlo sampling is exact — there's no intractable distribution to approximate, so MCMC isn't needed here.

2. **Regression** (`src/generators/regression_generator.py`)
   Fits one RandomForestRegressor per feature, predicting it from the others, on the training split. Synthetic rows are seeded from out-of-bag (OOB) predictions on that same split — each row predicted only by the trees that didn't bag it, so it's leakage-free without needing a separate held-out set — plus noise bootstrapped from the (honest, out-of-sample) OOB residuals, so outputs vary instead of collapsing to a deterministic point estimate. This keeps the engine self-contained on train, never touching the evaluation set.

3. **VAE** (`src/generators/vae_generator.py`)
   Learns a latent joint distribution over all features and samples new rows from its prior. Trained with the standard VAE ELBO (reconstruction loss + KL divergence to the standard normal, `beta` linearly annealed up from 0 over the first `kl_warmup_frac` of training) plus a covariance-matching term (`cov_weight`) that directly penalizes the difference between the reconstructed batch's covariance matrix and the real batch's.

Each engine's module exposes a single `generate(...)` function with a consistent calling convention.


## Architecture

```
src/
  configs/
    base.py                    # every config field, documented once, with sensible defaults/empty placeholders
    apple_quality.py            # imports base.py's defaults, overrides only what's dataset-specific
  generators/                  # physics_mc_generator, regression_generator, vae_generator — each exposes generate()
  evaluation/evaluate.py       # correlation heatmaps, PCA scatter, KS heatmap, p-value heatmap,
                                # ECDF overlay, volcano plot, summary metrics — all with human-readable labels
  config_loader.py             # resolves a config module by name — shared by every entry point below
  data_loading.py              # loads + cleans the source CSV for a given config — likewise shared
  main.py                      # runs all three engines, saves outputs, runs evaluation,
                                # prints a summary table, writes the report
  check_generalization.py      # standalone: re-checks already-generated synthetic data against
                                # train vs. test splits without re-running generation (see below)
results/<config_name>/
  synthetic_data/              # generated rows per engine, as CSV
  figures/correlation/         # correlation heatmaps (real + per engine) and the PCA scatter
  figures/marginals/           # KS heatmap, p-value heatmap, ECDF overlay, volcano plot
  summary_metrics.csv          # correlation-distance and mean-KS-stat per engine
  ks_marginals.csv             # per-feature KS statistic + p-value per engine
  generalization_gap.csv       # per-engine correlation distance vs. train split and vs. test split
reports/<config_name>/
  REPORT.md                    # auto-generated by main.py on every run — do not hand-edit, it gets
                                # overwritten each time `make run CONFIG=<config_name>` executes
```

Outputs are namespaced by config name so results from different datasets never overwrite each other.

### Adding a new dataset

Write a new module in `src/configs/` (copy `apple_quality.py` as a template): `from src.configs.base import *`, then override only what's dataset-specific — at minimum `DATA_PATH`, `FEATURES`, `ID_COLUMNS`, `LABEL_COLUMN`, `IS_PRE_SCALED`, `ROOT_VARIABLES`, `CAUSAL_GRAPH`, and ideally `DATA_SOURCE_URL` for provenance. Every field's meaning is documented once in `base.py`, which also carries sensible defaults for pipeline mechanics (`TEST_SIZE`, `N_SAMPLES`, `RANDOM_SEED`, `LATENT_DIM`, `VAE_EPOCHS`, `VAE_BETA`, `VAE_PATIENCE`, `VAE_HIDDEN_DIM`, `VAE_DROPOUT`, `VAE_FREE_BITS`, `VAE_COV_WEIGHT`, `VAE_USE_MINIBATCH`, `VAE_BATCH_SIZE`) — override those too if tuning calls for it. Run it with `make run CONFIG=<your_module_name>` (no `.py`, no changes to `main.py` needed — the config is selected at runtime, not hardcoded).

## Running it

```
make setup                       # create venv, install requirements
make run                         # runs the full pipeline for the default config (apple_quality)
make run CONFIG=<config_name>    # runs it for any other config module in src/configs/
make check-overfit               # re-checks the last run's synthetic data against train vs. test splits
```

`make run` logs the active config and each pipeline stage as it runs, prints a bordered summary table at the end (best value per metric marked, colored when run in an actual terminal), and rewrites `reports/<config_name>/REPORT.md` from that run's real numbers and figures. It also runs the generalization check described below and includes it in the report — `make check-overfit` re-runs just that check against already-generated synthetic data (no retraining), useful for a fast recheck without paying the full pipeline's cost again.

### Generalization check

Each engine's `correlation_euclidean_dist` is scored against the held-out test split — but any engine could, in principle, be fitting noise specific to the training split rather than real population structure. The check compares that same metric against the train split it was fit on vs. the test split it's scored on: a small gap is evidence of genuine generalization, a large one (especially train much better than test) would be a real overfitting signal. Results land in `results/<config_name>/generalization_gap.csv` and the report's "Generalization Check" section.

## Hypothesis

The core claim this project tests: a generative model, conditioned on the inputs that actually drive variability, can produce calibrated uncertainty estimates around its outputs. If true, synthetic individuals should exhibit realistic correlated properties — e.g. size, sweetness, and firmness co-varying the way they do in a real population — rather than looking like independent draws. Comparing the generative (VAE) engine against the physics-informed and regression engines is how we check whether that claim holds up.

## Research Question

Given observed measurements from a real population, can different modeling approaches generate synthetic individuals that preserve:

- Realistic feature distributions?
- Correlations between variables?
- Assumed causal relationships?
- Uncertainty in possible outcomes?

See `reports/<config_name>/REPORT.md` (e.g. `reports/apple_quality/REPORT.md`, `reports/mango_ripeness/REPORT.md`, `reports/banana_quality/REPORT.md`) for current results per dataset — methodology pulled live from each engine's own docstring, the results table, findings, and every figure this project produces, all regenerated fresh on the most recent `make run CONFIG=<config_name>`.
